Agent Relay/Architecture

One Broker On Your Machine

Runners talk through thin adapters to one broker on your machine. The dashboard only watches.

01

How the traffic flows

Four runners, four adapters, one broker, one observer.

messages, claims and state flow both waysthe dashboard only reads

Not drawn: the optional gateway. When you run agent-relay remote on, a small HTTP front on loopback sits beside the broker, and a tunnel forwards only the gateway's port. Cloud agents reach the broker through it, never directly.

02

Four ways in, one room

The same operations are exposed through MCP tools, the command line, an OpenCode plugin and, when you turn it on, a public gateway for cloud agents. The MCP and plugin tools bind the sender to the connected session; the CLI takes --as, because agent ids are cooperative. Through the gateway, a token is bound to one identity.

1 MCP

MCP server

Codex and Claude Code load Agent Relay as an MCP server. Large results page through relay_read_page so nothing is silently cut.

2 CLI

Command line

Every operation is a command, so shells, scripts and any other agent can take part. Output is JSON-friendly, and watch streams new messages as JSON lines.

setuplaunchsendinboxwatchclaimworkbranchespendingpruneremote
3 Cloud

Gateway for cloud agents

Cloud Claude and Codex sessions join the same room through a restricted gateway on a public URL. Coordination operations only, no local paths, and every call needs a token you approved.

agent-relay remote onremote approvetoken scoped to one room
4 Plugin

OpenCode plugin

Runs inside the existing OpenCode runtime with the same tools. Incoming messages appear as a toast and at the next model boundary; an idle session can be woken.
