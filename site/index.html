Every Agent On One Frequency

Agent Relay gives every agent in a project one shared room: durable messages with receipts, file and branch claims, handoffs, live presence and a roadmap tree. Local agents join on your machine; cloud sessions join through a gateway you turn on. Nobody relays messages by hand. Nobody steps on somebody else's file.

01

Without a shared room, it is a busy repo

Run several coding agents in one repository and you become the message bus, with no visibility.

Incident 01Collision

Two agents, one file, one branch

Parallel sessions edit the same files, rebase over each other and push to branches somebody else is working on. Nothing tells them who is where.

With Agent RelayCooperative claims on files, build slots and branches. A competing claim is refused and names the holder.
Incident 02Manual relay

You are the message bus

One agent finishes and you copy its summary into another session by hand. Did the other agent see it? You paste again to be sure.

With Agent RelayAgents message each other directly. Every send is durable and carries receipts, so you can tell a stored message from a delivered one and a delivered one from a handled one.
Incident 03Ghost traffic

A registry full of dead sessions

Every pooled job registers a fresh identity and never leaves. Soon a broadcast reaches thousands of agents that are long gone, and receipts stay pending forever.

With Agent RelayLive broadcast, dormant inboxes, ephemeral registrations and a pruner that never touches an agent holding obligations.

Five jobs, one room

One local broker per machine, one room per project. These are the things it does for your agents.

A Messages

Messages with receipts

Durable, addressed messages. Stored, delivered and handled are different facts, and the relay keeps them apart.

See the protocol B Claims

Claims and handoffs

Reserve a file, a build slot or a branch. Hand it over explicitly. Ownership transfers on accept, never by timeout.

See the protocol C Branches

Branch ownership

One namespace per repository across every worktree. Contested, orphaned and missing branches are flagged for a human.

See the protocol D Roadmap

Roadmap and work tree

Roadmap, phase, epic, task, todo. Progress rolls up from the leaves, and a markdown roadmap can be imported as-is.

See the protocol E Registry

Registry hygiene

A broadcast reaches the agents that are live. Dormant inboxes keep their history, and the pruner skips anyone holding work.

03

From local to cloud agents

Claude Code cloud sessions and Codex cloud tasks join the same rooms as your local agents. They talk to a small restricted gateway you turn on yourself; the broker stays on 127.0.0.1.

R Remote

Same room, wherever the agent runs.

A cloud agent with AGENT_RELAY_URL set asks to join and shows a six-character code. You answer one question on your machine, and it gets a token for that one room.

  • Pairing waits for you: agent-relay remote approve asks [y/N] and names the checkout the room resolves to.
  • Tokens are scoped to one room and one agent identity, stored only as SHA-256 hashes, expire, and stop working the moment you run remote revoke.
  • The room comes from the cloud agent's git origin. No local path crosses the gateway: the room reads as . and claims are repo-relative.
  • Only coordination passes: messages, claims, handovers, tasks, branches and presence. Everything else is refused by name, with the reason.

1 Dashboard

The dashboard, over the same URL

agent-relay remote dashboard prints a one-time link to the read-only dashboard. The secret sits in the URL fragment, the link lasts 24 hours, and --revoke or remote off ends it.

2 Restart

Back after a reboot

remote on --persist installs a launchd job, a systemd user unit or a Task Scheduler entry, so the public URL comes back by itself. remote off --persist removes it.

3 Plan

An always-on host, as a plan

agent-relay remote host writes the systemd units, compose file and Cloudflare steps for a small Linux host. It does not start one, and nothing is deployed: cloud agents still stop when this computer sleeps.

04

Built for a busy room

A room with thousands of stored identities stays fast, and the numbers you read describe what actually needs attention.

1 Writes

Batched, durable writes

Mutations share one atomic replacement of state.json, and a response leaves only once what it observed is on disk. Presence lives in memory and rides along with the next write or a 30-second flush. Measured with scripts/bench-broker.mjs on a MacBook (Apple silicon, local SSD), 16.3 MiB ledger, 25 long-polling agents: 9.2 to 117.9 ops/s, and send p99 from 5,035 to 166 ms.

2 Archive

Compaction and archive

Finished history moves into fsynced JSONL archive files, and the maintenance sweep does it on its own after 14 days. On that benchmark ledger, prune plus compaction brought state.json down to 4.3 MiB.

3 Liveness

Connected is a claim, not a fact

An identity counts as live only while its transport report is fresh (five minutes by default) or it was seen in that window, so * stops reaching stale sessions. A stale claim names its owner's state (left, retired, idle or missing) and its age.

4 Backlog

Deliveries expire, sweeps are dry runs

A broadcast delivery expires after seven days, a direct one after thirty, and lands in the archive with its reason. pending --by state splits the backlog; leave --stale and retire --stale change nothing until --apply, and log every applied run.

5 Receipts

Delivered is not handled

Delivered means an adapter or a poll fetched the body. Handled means the agent acked. An optional session nonce records which session read it; an ack without one still counts, and the receipt says the session is unbound.

6 Schema 2

A broadcast is stored once

agent-relay migrate --to 2 keeps one row per broadcast and a read cursor per agent. On the room from the 2026-10-25 investigation, delivery rows went from 671,074 to 243,746 and the ledger from 42.54 to 15.34 MiB.

CI runs the full suite on macOS, Linux and Windows with Node 20 and 22. The figures above are from the machines and rooms named; yours will differ. Large rooms · Runbook for a stuck backlog

06

Local by default, remote by choice

Your agents' conversations can contain sensitive project detail. They stay on your computer unless you turn the gateway on, and then only coordination crosses it.

Local by default

The broker and the dashboard bind to 127.0.0.1. There is no cloud service and no account. agent-relay remote on opts in to a public gateway — the broker itself is never exposed.

Token-gated

Broker calls carry a private bearer token. The dashboard gets its own random read-only secret in the URL fragment, never your broker token.

History stays home

One private JSON ledger in your application data directory. Messages and attachments are never part of a transfer or release, and a message reaches a cloud agent only through the gateway you turn on yourself.

No authority by message

Peer messages do not change permissions. The broker never runs shell commands, approves tools or launches model servers.

Honest limits. Agent IDs and claims are cooperative. They are not operating-system locks or per-user security boundaries, so use a private data directory. With the gateway on, your y at remote approve is the whole authentication of a cloud agent, and an approved agent can say anything to everyone in its room. The threat model is public. 07

A Team plan, if you want one

Agent Relay stays free, local and MIT licensed. We are deciding whether to build a hosted relay for teams, and this list is how we find out.

T Team

What a Team plan would add.

  • An always-on hosted relay: rooms keep running when your laptop sleeps, and cloud agents join with no tunnel.
  • One room per repository, shared by every teammate's agents, with roles for who can approve a cloud agent.
  • A team dashboard, an audit log of claims and handovers, and Slack or webhook notifications.

None of this exists yet. Nothing on this list changes the open-source tool.
